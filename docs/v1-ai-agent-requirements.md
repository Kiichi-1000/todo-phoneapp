# AIエージェント機能 要件定義書

最終更新: 2026-05-05
ステータス: ドラフト（要レビュー）
提供形態: **完全有料機能**（無料枠なし、サブスクリプション契約者のみ利用可能）

---

## 1. 目的・背景

ToScheの利用体験を「タップ・入力中心」から「会話で指示できる」へ拡張する。
ユーザーは自然文でAIに話しかけることで、タスク追加・スケジュール登録・リマインダー設定などを行える。

期待効果:

- 入力ステップ削減（複数の画面遷移を1メッセージで完結）
- 思いついた時に音声/テキストで素早く登録できる体験
- 既存ToDo・スケジュール機能の利用率向上

## 2. スコープ

### フェーズ1（MVP・本要件定義の対象）

| # | 機能 | 概要 |
|---|------|------|
| F1 | チャットUI | 専用画面でAIとテキスト対話 |

| F3 | スケジュール作成 | 「明日10時から12時まで会議入れて」→ schedules に追加 |
| F4 | リマインダー設定 | 既存タスクに開始時間を設定 |
| F5 | 一覧確認 | 「今日のタスクは？」「今週の予定は？」 |
| F6 | 完了/削除 | タスク完了マーク、タスク/予定の削除（確認付き） |
| F7 | 確認フロー | 破壊的操作（削除）と曖昧な指示は実行前にユーザー確認 |
| F8 | 課金・サブスクリプション | アップグレード画面、購読ステータス、フィーチャーゲート |
| F9 | 利用上限管理 | 月次メッセージ数のカウント・上限到達時の制御 |

### フェーズ2（将来拡張・対象外だが拡張余地は確保）

- ルーチン操作（追加・スキップ・完了）
- ワークスペースのエリア名編集・タイプ切替
- 複数ステップを1メッセージで連続実行（例: 「明日のタスク3つまとめて作って…」）
- 音声入力（Whisper等のSTT統合）
- 提案・リマインドのプロアクティブ通知

### 対象外（明示的に作らない）

- AIによる優先度自動判定/タスク自動並べ替え
- カレンダー連携（Google Calendar等）
- AIエージェントのチーム共有
- AIによる外部Web検索

## 3. ユーザーストーリー（代表例）

1. **タスク追加（朝の通勤中）**: 「今日中に経費精算」と入力 → 今日のワークスペースにタスクが追加される
2. **予定登録**: 「明日14時から1時間、歯医者の予定」 → 明日の14:00-15:00 のスケジュールが登録される
3. **リマインダー追加**: 「経費精算のタスク、12時に通知して」 → 既存のタスクを特定し reminder_at に設定
4. **状況確認**: 「今日まだ終わってないタスクは？」 → 未完了のタスク一覧をリスト表示
5. **取り消し**: 「さっき作った会議の予定を消して」 → 直前作成スケジュールを削除前に確認

## 4. 機能要件

### 4.1 チャットUI（F1）

- 配置: タブバーに新規タブ「AI」を追加（`app/(tabs)/ai.tsx`）
- メッセージリスト + 入力欄 + 送信ボタン
- ストリーミング表示（AI応答をトークン単位で逐次表示）
- AIが実行した操作を構造化カードで表示（タスクカード/予定カード）し、対象画面へ遷移可能
- 会話履歴: フェーズ1ではセッション内のみ保持（DB保存はフェーズ2）
- 「履歴クリア」ボタン

### 4.2 AIが実行できる操作（ツール定義）

LLMの Tool Use（Function Calling）で実装。各ツールはユーザーの認証コンテキストを通じてSupabaseのRLSを経由し、他人のデータには触れない。

| ツール名 | パラメータ | 用途 |
|---------|-----------|------|
| `list_todos` | `date?`, `only_incomplete?` | タスク一覧取得 |
| `create_todo` | `content`, `date?`, `grid_area?`, `reminder_at?` | タスク追加 |
| `update_todo` | `todo_id`, `content?`, `is_completed?`, `reminder_at?` | タスク更新 |
| `delete_todo` | `todo_id` | タスク削除（要確認） |
| `list_schedules` | `date` or `date_from` + `date_to` | 予定一覧取得 |
| `create_schedule` | `date`, `start_minutes`, `end_minutes`, `title`, `color?` | 予定追加 |
| `update_schedule` | `schedule_id`, `start_minutes?`, `end_minutes?`, `title?` | 予定更新 |
| `delete_schedule` | `schedule_id` | 予定削除（要確認） |
| `get_current_context` | なし | 今日の日付・現在時刻・直近のワークスペース情報をAIへ渡す |

ツールはAIが必要に応じて複数回呼び出せる（例: list で対象を特定 → update で更新）。

### 4.3 確認フロー（F7）

| 操作種別 | 確認 |
|---------|------|
| 作成（create_*） | 不要・実行後に結果カード表示 |
| 更新（update_*） | 対象が一意に特定できれば不要、複数候補あれば確認 |
| 削除（delete_*） | 必ず確認ダイアログ |

確認はAIが「これでよろしいですか？」と問い、ユーザーが「はい」と答えたら次ターンでツール実行する設計（ツール呼び出し前に承認）。

### 4.4 入力解釈ルール

- 相対日時（「明日」「今週末」「3時間後」）は AIが `get_current_context` で取得した現在時刻を基準に絶対日時へ変換
- 時刻が曖昧な場合（「夜」など）はデフォルト値を提示（例: 夜=20:00）し確認
- ワークスペースエリア指定がない場合は `grid_area = null`（自由配置 / 個別ポストイット）として作成

## 5. 非機能要件

### 5.1 性能

- 初回応答（ストリーム開始）: 3秒以内
- ツール実行込みのターン完了: 10秒以内（目標）
- メッセージ送信失敗時のリトライ: 自動1回 + 手動再送ボタン

### 5.2 コスト

- 使用モデル: `claude-haiku-4-5`（高速・低コスト）をデフォルト、必要に応じて `claude-sonnet-4-6` 切替
- システムプロンプト・ツール定義はプロンプトキャッシュで再利用
- 1ターンあたりのツール呼び出し最大: 5回（無限ループ防止）
- 1メッセージの最大入力: 2000文字
- 月次のユーザー単位のメッセージ数上限を設ける（運用後に調整）

### 5.3 プライバシー

- ユーザーのタスク・予定は本人のみ操作可（既存RLSが保証）
- 会話内容はAnthropic API送信時に暗号化（HTTPS）
- DB保存はフェーズ1では行わない（フェーズ2で導入時はオプトイン）
- システムプロンプトをユーザーに公開しない

### 5.4 エラーハンドリング

- AnthropicAPI失敗時: ユーザーに「AIが一時的に応答できません」と表示
- ツール実行失敗時: AIが理由を要約して再提案（例: 「指定の時間と重複する予定があります」）
- ネットワーク断: ローカルでメッセージ保持し再送可能に

### 5.5 セキュリティ

- AnthropicのAPIキーはサーバー側（Supabase Edge Function）の環境変数のみ。クライアントには出さない
- ユーザー認証JWTをEdge Functionで検証し、`auth.uid()` を強制
- ツールのSQL実行は型付きSupabaseクライアント経由のみ（生SQL不可）
- プロンプトインジェクション耐性: ツール呼び出しの権限はサーバー側でユーザーIDに固定し、ユーザーが他人のIDを指示しても無効

## 6. アーキテクチャ

### 6.1 技術スタック

| レイヤ | 採用 |
|-------|------|
| クライアント | React Native (Expo) — 新規画面 `app/(tabs)/ai.tsx` |
| バックエンド | Supabase Edge Function (Deno/TypeScript) |
| LLM | Anthropic Claude API（`claude-haiku-4-5` メイン） |
| 機能 | Tool Use, Streaming (SSE), Prompt Caching |
| DB | 既存Supabase Postgres（schedules, todos など） |
| 認証 | 既存Supabase Auth |

### 6.2 リクエストフロー

```
[App] -- POST /ai-chat (JWT, messages) --> [Edge Function]
[Edge Function] -- Claude API (stream + tools) --> [Anthropic]
[Anthropic] --> [Edge Function]
  ├─ tool_use → Edge Function が Supabase で実行 → 結果をtool_resultとして返送
  └─ text → そのままSSEでクライアントへストリーミング
[Edge Function] -- SSE chunks --> [App]
```

### 6.3 データモデル変更

フェーズ1では既存テーブルへの変更なし。

フェーズ2で会話履歴を保存する場合の想定:

- `ai_conversations` (id, user_id, created_at, title)
- `ai_messages` (id, conversation_id, role, content, tool_calls jsonb, created_at)
- 両テーブルに `auth.uid() = user_id` のRLSを設定

### 6.4 ファイル配置（実装時の想定）

| パス | 役割 |
|-----|------|
| `app/(tabs)/ai.tsx` | チャット画面 |
| `components/AIChatMessage.tsx` | メッセージ吹き出し |
| `components/AIToolResultCard.tsx` | ツール実行結果カード |
| `lib/aiClient.ts` | Edge FunctionへのSSEクライアント |
| `supabase/functions/ai-chat/index.ts` | Edge Function本体 |
| `supabase/functions/ai-chat/tools.ts` | ツール定義とSupabase実行ロジック |
| `supabase/functions/ai-chat/prompt.ts` | システムプロンプト |

## 7. 料金設定・コスト試算（トークンチャージ方式）

### 7.1 課金モデル概要

ユーザーは月額料金を支払い、その対価として **円ベースのAIトークン残高** を受け取る。実際に消費されるのは Claude / OpenAI の API トークンだが、**ユーザー画面では「残り◯円分」とのみ表示** することで分かりやすくする。

### 7.2 プラン構成

#### 月額プラン

| プラン | 月額（税込） | 月次付与トークン価値 | 月間ターン目安 |
|-------|------------|------------------|--------------|
| **AI ライト** | **¥1,000** | **¥500分** | 約330ターン（約11ターン/日） |
| **AI スタンダード** | **¥2,000** | **¥1,000分** | 約670ターン（約22ターン/日） |

ターン数は1ターン平均約 **¥1.5** で換算した目安（後述の原価試算）。実際の消費は会話の長さで変動する。

#### 長期契約プラン（割引適用）

| プラン | 半年（税込） | 半年割引 | 年間（税込） | 年間割引 |
|-------|------------|---------|------------|---------|
| AI ライト | **¥5,500** | 約8% | **¥10,000** | 約17% |
| AI スタンダード | **¥11,000** | 約8% | **¥20,000** | 約17% |

長期契約でも **トークンは月次付与**（一括前倒し付与は行わない）。原価リスクの抑制が目的。

例: AI ライト年間 ¥10,000 → 月割換算 ¥833 → 毎月 ¥500分のトークンが12ヶ月付与される。

### 7.3 トークンの内部換算ルール

- **内部レート: ¥150/$ 固定**（四半期ごとに見直し、利用規約で改定権を明記）
- API実コストは Anthropic / OpenAI の公開USD価格を内部レートで円換算し、残高から差し引く
- **ユーザー画面の表示は円のみ**（例: 「残り 432円分」）
- 内部DBはトークン数も併せて記録（監査・原価分析用）

#### 1ターンあたりの想定消費

採用モデル: `claude-haiku-4-5`（メイン）

| 種別 | トークン数 | 単価（USD/Mトークン） | コスト |
|------|----------|------------------|-------|
| キャッシュ読込（system + tools） | 3,000 | $0.10 | $0.0003 |
| 新規入力（履歴 + ユーザー文） | 1,500 | $1.00 | $0.0015 |
| ツール往復（input + output） | 2,000 | 平均 $2.00 | $0.0040 |
| 最終出力 | 300 | $5.00 | $0.0015 |
| **合計（1ターン）** | | | **$0.0073（約¥1.1）** |

安全マージンを乗せ、**1ターン = ¥1.5** で残高引き落とし。

### 7.4 トークン繰越（キャリーオーバー）

- 当月付与分のうち未使用分は **翌月のみ繰越可能**、翌々月初に失効
- 月初に新規付与 + 前月繰越分 = 当月利用可能枠

#### 例（AIライト・¥500/月付与）

| 月 | 期初付与 | 前月繰越 | 利用可能 | 当月消費 | 翌月へ繰越 |
|----|--------|---------|---------|---------|-----------|
| 1月 | ¥500 | ¥0 | ¥500 | ¥300 | ¥200 |
| 2月 | ¥500 | ¥200 | ¥700 | ¥600 | ¥100（2月分の残） |
| 3月 | ¥500 | ¥100 | ¥600 | ¥500 | ¥100 |

**重要**: 1月の繰越¥200のうち2月で使い切れなかった分は3月へは引き継がれない。常に「直近1ヶ月分」のみ繰越。

### 7.5 配信手数料の前提

- iOS / Android: アプリ内課金 **30%**（Apple Small Business Program / Google Play 1M USD以下条件で **15%**）
- Web (Stripe): **3.6% + ¥40/件**
- 本試算は保守的に **30%** で計算

### 7.7 平均ユーザーの実利益見込み

業界経験則として **平均ユーザーは付与上限の30〜50%しか消費しない**。最悪ケースの試算より粗利は1.5〜2倍見込める。

例: AI ライト・平均ユーザー（付与の40%消費）・ストア手数料15%

- 売上正味 ¥850 - 実消費 ¥200 - 運用 ¥50 = **粗利 ¥600（粗利率 60%）**

### 7.8 赤字防止策（必須）

1. **トークン残高ハード上限**: 残高ゼロで送信不可、AIが「今月のトークンを使い切りました」と通知
2. **1ターンあたりの上限**:
   - 入力: 8,000トークン
   - ツール呼び出し: 1ターン最大5回
   - 出力: 1,000トークン
3. **異常検知レート制限**: 1ユーザーが1日 ¥100分超を消費した場合は警告、¥200分超で当日停止
4. **使用モデル固定**: `claude-haiku-4-5` を標準とする。`sonnet` / OpenAI モデルは別プラン化または個別オプションで提供
5. **為替変動バッファ**: 内部レート ¥150/$ は四半期ごとに見直し可能と利用規約に明記
6. **繰越期限の厳守**: 翌月初に未使用分を自動失効させ、長期蓄積による負債化を防止

### 7.9 提案の評価（Claude側コメント）

**良い点**:

- ユーザーから見て「払った金額の半分はAI利用に充当される」という構造で **透明性が高い**
- 月額 ¥1,000 / ¥2,000 という **心理的ハードルの低い価格設定**
- 1ヶ月繰越で「今月使えなかった分が無駄にならない」という **UX上の安心感**
- 年間契約で **収益の予測性向上 + 解約抑制**

**注意点・リスク**:

- AI ライト ¥1,000 プランは **ストア手数料30%だと粗利率15%とタイト**。Apple Small Business Programの適用申請を必須とする
- トークン制度は **実装複雑度が高い**（残高 / 取引履歴 / 繰越 / 失効の正確な記録、リアルタイム表示）→ 開発工数 +3〜4日
- ユーザーが「トークン」概念を理解する **学習コスト**がある → 「残り◯円分」表示で吸収
- **為替変動リスク**は依然存在。¥150/$ から大幅にずれた場合は速やかにレート改定
- 「Claude / OpenAI トークン」と複数モデル対応を謳う場合、内部実装の抽象化が必要 → 最低限 Claude のみで開始し、OpenAI は将来対応とする選択肢も

### 8.4 データモデル

#### 8.4.1 サブスクリプション

```sql
CREATE TABLE user_subscriptions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL UNIQUE REFERENCES auth.users(id),
  status text NOT NULL CHECK (status IN ('active','trialing','past_due','canceled','expired')),
  plan text NOT NULL CHECK (plan IN ('ai_light','ai_standard')),
  billing_cycle text NOT NULL CHECK (billing_cycle IN ('monthly','half_year','yearly')),
  product_id text NOT NULL,
  platform text NOT NULL CHECK (platform IN ('ios','android','web')),
  current_period_start timestamptz NOT NULL,
  current_period_end timestamptz NOT NULL,
  next_grant_at timestamptz NOT NULL,
  revenuecat_user_id text,
  stripe_subscription_id text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

`next_grant_at` は次回トークン付与予定（毎月の課金期間境界）。

#### 8.4.2 トークン残高

```sql
CREATE TABLE ai_token_balances (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL UNIQUE REFERENCES auth.users(id),
  current_grant_yen numeric(10,2) NOT NULL DEFAULT 0,        -- 当月付与分の残額
  current_grant_expires_at timestamptz,                      -- 当月分の失効予定
  carryover_yen numeric(10,2) NOT NULL DEFAULT 0,            -- 前月繰越分の残額
  carryover_expires_at timestamptz,                          -- 繰越分の失効予定
  total_granted_yen numeric(12,2) NOT NULL DEFAULT 0,        -- 累計付与額
  total_consumed_yen numeric(12,2) NOT NULL DEFAULT 0,       -- 累計消費額
  total_expired_yen numeric(12,2) NOT NULL DEFAULT 0,        -- 累計失効額
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

利用可能残高 = `current_grant_yen + carryover_yen`（共に未失効）。

#### 8.4.3 トークン取引履歴

```sql
CREATE TABLE ai_token_transactions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users(id),
  kind text NOT NULL CHECK (kind IN ('grant','carryover','consume','expire','refund','admin_adjust')),
  amount_yen numeric(10,4) NOT NULL,                         -- consume/expire/refundは負値
  balance_after_yen numeric(10,2) NOT NULL,
  api_provider text CHECK (api_provider IN ('anthropic','openai')),
  api_model text,
  input_tokens int,
  output_tokens int,
  cache_read_tokens int,
  cache_write_tokens int,
  conversation_id uuid,
  message_id uuid,
  metadata jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_token_tx_user_created ON ai_token_transactions(user_id, created_at DESC);
```

すべての残高変動を記録。監査・原価分析・ユーザー履歴表示に使用。

全テーブルRLS有効化、`auth.uid() = user_id` のポリシー。

### 8.5 トークン付与・繰越バッチ

毎月の課金期間境界（`next_grant_at`）でトリガーする月次バッチ:

1. **当月分の失効処理**: `current_grant_yen` のうち未使用分を `carryover_yen` へ移動（前月繰越があれば失効）
2. **新規付与**: プランに応じて `current_grant_yen` を `¥500` または `¥1,000` で再設定
3. **取引記録**: `expire`（失効分）、`carryover`（繰越分）、`grant`（新規付与）の3レコードを `ai_token_transactions` へ追加
4. **`next_grant_at` を翌月に更新**

実装手段:

- **Supabase Cron** で日次実行 → `next_grant_at <= now()` のユーザーを処理
- またはチャット送信時に Edge Function 内で「期限超過なら付与処理」を遅延実行（コスト効率優先）

### 8.6 状態同期フロー

```
[App] purchase → [Apple/Google] → [RevenueCat]
                                        |
                                        v
                                [RevenueCat Webhook]
                                        |
                                        v
                  [Supabase Edge Function `revenuecat-webhook`]
                                        |
                                        v
            [user_subscriptions 更新 + ai_token_balances 初期付与]
```

- アプリ起動時に RevenueCat SDK で `customerInfo` を取得し、`user_subscriptions` と整合性チェック
- Webhook で更新・解約・支払失敗をリアルタイム検知
- 解約時はトークン残高をそのまま据え置き（期限内なら使い切れる）、`current_period_end` 経過後に失効

### 8.7 フィーチャーゲート（メッセージ送信時のチェック順）

1. ログイン済みか
2. `user_subscriptions.status` が `active` または `trialing` か
3. `current_period_end > now()` か
4. **利用可能残高 ≥ 1ターン分（¥1.5）** か
5. 1日のレート制限内か（¥200分/日上限）

未充足ならアップグレード画面 / トークン枯渇画面 / レート制限画面に誘導。

### 8.8 法的・運営要件

- **特定商取引法表示**（自動更新サブスクの表示義務）: プラン詳細・アップグレード画面に明示
- 解約手順の明示（プラン詳細・購入時画面・サブスク管理画面の3箇所）
- 利用規約に以下を明記:
  - 料金変更条項（内部レート見直し含む）
  - トークン繰越ルール（1ヶ月のみ）
  - 解約時のトークン取り扱い（使用期限内に消費可、返金なし）
  - API障害時の運営方針
- 領収書発行（自動メール送信）
- **トークンの法的位置付け**: 「サービス利用権の引換単位」として規約に定義（前払式支払手段ではない設計とする — 関連法規制を回避）

## 11. リスクと対策

| リスク | 対策 |
|-------|------|
| LLMが架空のtodo_idを生成して操作失敗 | ツールはRLSで他人のデータを触れない+IDが存在しない場合はエラーをAIに返して再試行させる |
| 想定外の量のAPIコスト | ユーザー単位のレート制限・トークン残高ハード上限・キャッシュ徹底 |
| 自然言語の曖昧さで誤った日時設定 | AIは確定前に必ずユーザーへ復唱確認、相対日時は絶対日時に変換して表示 |
| プロンプトインジェクション | ユーザーIDはサーバー側で固定、他ユーザー操作要求は拒否 |
| API障害 | エラーメッセージで明示・通常UIで操作可能なことを案内 |
| **円安進行でAPI原価が想定超過** | 内部レート¥150/$を四半期見直し、利用規約に料金/レート変更条項を明記 |
| サブスク状態の同期失敗 | RevenueCat Webhook + アプリ起動時の `customerInfo` 二重チェック |
| ストア審査でリジェクト | アップグレード画面に必須項目（特商法・解約手数料・復元）を全て掲載、トークン規約をプライバシーポリシーに記載 |
| トライアル悪用（連続再購読） | Apple/Googleはユーザー単位でトライアル1回制限、これを利用 |
| **トークン残高の二重消費・整合性破壊** | DB側でTRANSACTIONを使用、`ai_token_transactions` への INSERT と `ai_token_balances` の UPDATE をアトミックに実行 |
| **付与・繰越バッチの実行漏れ** | Cron + 遅延実行のフォールバック2系統。送信時に `next_grant_at <= now()` なら付与処理を即時実行 |
| **トークンが「前払式支払手段」と判定される法的リスク** | 規約で「サービス利用権の引換単位」と明記、第三者譲渡不可・現金返金不可を明記 |
| **AI ライト¥1,000プランの低粗利** | Apple Small Business Program 適用で15%手数料を確保、適用前は値上げまたはプラン廃止を選択肢に |
| **長期契約途中の値上げトラブル** | 契約期間中は契約時の付与額を保証、改定は新規契約・更新時から適用 |

## 12. 受け入れ基準（MVP）

### 12.1 機能基準

以下のシナリオが成功すれば MVP 完了:

1. 「今日中に資料作成のタスク追加して」→ 今日のワークスペースにタスクが追加され、確認カードが表示される
2. 「明日10時から12時まで企画会議を入れて」→ 明日のスケジュール画面（リスト・円グラフ両方）に表示される
3. 「資料作成のタスクに14時のリマインダーをつけて」→ 該当タスクの reminder_at が設定され、開始時間通知の予約が走る（設定でON時）
4. 「今日のタスクは？」→ 未完了タスクを箇条書きで返す
5. 「企画会議の予定削除して」→ 確認ダイアログ後に schedules から削除される
6. 他人のタスクIDを指定しても操作できない（RLSで拒否される）

### 12.2 課金基準

7. 未契約ユーザーがAIタブをタップ → アップグレード画面（月額/半年/年間 × ライト/スタンダードの計6プラン）が表示される
8. iOS/Android で購入完了 → `user_subscriptions.status = active` が反映され、初回トークン（¥500分または¥1,000分）が即時付与される
9. RevenueCat Webhook で解約検知 → `current_period_end` 経過後にAIタブが利用不可になる
10. 別端末で復元購入 → 同一ユーザーの購入状態が反映される
11. 解約後も有効期間内は利用可能、期間終了で停止

### 12.3 トークン基準

12. チャット画面に「残り◯円分」が常時表示される
13. メッセージ送信ごとに残高が消費額分減少し、`ai_token_transactions` に記録される
14. 残高ゼロで送信不可、トークン枯渇画面に誘導される
15. 月初の付与タイミングで前月分が繰越され、前々月の繰越分は失効する（取引履歴に記録）
16. 1日¥200分超を消費しようとするとレート制限される

### 12.4 経済性基準

17. ヘビーユーザー（付与額を100%消費）でも1人あたり月次粗利が **¥150以上**（ストア手数料30%時）
18. Apple Small Business Program 適用後は粗利率 **30%以上** を維持
19. 平均ユーザー（付与の40%消費）の粗利率が **50%以上**

---

以上。ユーザー提案（¥1,000で¥500分・¥2,000で¥1,000分・年間半年契約・1ヶ月繰越）を採用した完全有料モデルでの要件定義。レビュー後、未決事項（第9章）の方針確定 → 詳細設計 → 実装、の順で進める想定。
