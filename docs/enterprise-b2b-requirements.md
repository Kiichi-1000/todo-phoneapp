## 0. エグゼクティブサマリー

ToScheの個人向けタスク管理アプリをベースに、企業内での **目標カスケード型タスク管理 + AI支援** を提供するSaaSプロダクトを定義する。

**3階層モデル**で市場を網羅：

| 層 | 商品 | 顧客 | 価格 | データ分離 |
|---|---|---|---|---|
| **L1: Personal** | ToSche（既存） | 個人 | ¥0 / ¥1,000-2,000/月 | 個人内 |
| **L2: SMB** | ToSche **+ Biz拡張機能** | 5〜30名の中小企業・店舗 | **初期¥300,000 + 月¥50,000-60,000** | RLS による論理分離 |
| **L3: Enterprise** | ToSche **for Biz**（別アプリ） | 50名以上の本格運用 | **初期¥1,000,000 + 月¥500,000〜** | 専用Supabaseインスタンス（オプション） |

3層構造により、価格幅 250倍 で多様な企業ニーズを吸収。粗利率 70-85% 想定。

## 2. 認証・アカウント構造 ⭐最重要

### 2.1 概念モデル

```
[User] (auth.users) ─┬─ Personal context (個人モード)
                     └─ Membership(s) ─→ [Organization] ─┬─ Subscription
                          ├─ role                         ├─ Settings
                          └─ permissions (JSONB)          └─ Branding
```

1人のユーザーは **0個以上の組織に所属可能**。常に **個人モード + N個の組織モード** を切替できる「コンテキスト」概念で運用。

### 2.2 ログインフロー

```
[起動]
   ↓
┌────────────────────────────────────┐
│ ToSche へようこそ                   │
│  [👤 個人で使う]                   │
│  [🏢 企業契約で使う]               │
└────────────────────────────────────┘
   ↓ 企業を選択
┌────────────────────────────────────┐
│ 企業コード: [_________________]     │ ← 8〜12桁の英数字
│ 認証番号:   [_________________]     │ ← 招待コード or 個人IDPW
│  [ログイン]                        │
└────────────────────────────────────┘
   ↓ 認証成功 → 組織コンテキストに入る
   ↓
┌────────────────────────────────────┐
│ コンテキスト切替（ヘッダー）         │
│ • 株式会社 ABC（管理者）           │
│ • 株式会社 XYZ（メンバー）         │
│ • 👤 個人モード                    │
└────────────────────────────────────┘
```

### 2.3 認証3パターン

| パターン | 用途 | 認証フロー |
|---|---|---|
| **A. 招待コード認証** | 新入社員のオンボーディング | 企業コード + 招待コード → メール/SMS確認 → パスワード設定 → 組織メンバー化 |
| **B. SSO（L3のみ）** | 大企業 | 企業コード → SAML / Google Workspace / Microsoft Entra ID リダイレクト → SSO成功で自動メンバー化 |
| **C. ハイブリッド（個人+企業）** | 既存個人ユーザーが入社 | 既存メールでログイン → 「組織を追加」→ 企業コード+招待コード入力 → 既存個人アカウントに組織メンバーシップが追加 |

### 2.4 データモデル

```sql
-- 組織
CREATE TABLE organizations (
  id uuid PRIMARY KEY,
  code text UNIQUE NOT NULL,          -- 「企業コード」(例: ABC-2026-7M3K)
  name text NOT NULL,
  plan text NOT NULL,                  -- 'smb' | 'enterprise'
  status text NOT NULL,                -- 'active' | 'suspended' | 'trial'
  billing_email text,
  ai_monthly_budget_yen numeric,       -- AI課金上限
  branding jsonb,                      -- ロゴ・カラー・カスタムドメイン等
  data_isolation text DEFAULT 'shared', -- 'shared' | 'dedicated' (L3 で専用)
  created_at, updated_at
);

-- メンバーシップ（1ユーザー × N組織）
CREATE TABLE organization_members (
  user_id uuid REFERENCES auth.users,
  org_id uuid REFERENCES organizations,
  role text NOT NULL,                  -- 'owner' | 'admin' | 'manager' | 'member'
  permissions jsonb NOT NULL,          -- 細かい権限フラグ
  joined_at, deactivated_at,
  PRIMARY KEY (user_id, org_id)
);

-- 招待コード（認証番号）
CREATE TABLE organization_invites (
  code text PRIMARY KEY,               -- 6〜10桁、ランダム生成
  org_id uuid REFERENCES organizations,
  preset_role text,
  preset_permissions jsonb,
  valid_until timestamptz,
  max_uses int DEFAULT 1,
  used_count int DEFAULT 0,
  created_by uuid REFERENCES auth.users
);

-- AI課金経路決定（個人 or 組織のどちらの予算を引くか）
CREATE TABLE ai_billing_context (
  user_id uuid PRIMARY KEY,
  active_org_id uuid NULL,             -- NULLなら個人モード
  set_at timestamptz
);
```

### 2.5 RLS（Row-Level Security）方針

全テーブルにRLSポリシー必須。組織データは、メンバーシップ確認 + role/permissions 検査の二段階。

```sql
-- 例: 組織目標の閲覧
CREATE POLICY "Members can view org goals"
  ON organization_goals FOR SELECT TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM organization_members
      WHERE org_id = organization_goals.org_id
        AND user_id = auth.uid()
        AND deactivated_at IS NULL
    )
  );

-- 例: 編集権限を持つメンバーのみ編集可
CREATE POLICY "Hosts can edit org goals"
  ON organization_goals FOR UPDATE TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM organization_members
      WHERE org_id = organization_goals.org_id
        AND user_id = auth.uid()
        AND (permissions->>'goal_edit')::boolean = true
    )
  );
```

## 3. 権限管理 ⭐重要

### 3.1 4階層ロール（プリセット）

| ロール | 想定 | デフォルト権限 |
|---|---|---|
| **Owner（経営者）** | 社長 / 創業者 | 全権限 + 課金管理 + 組織削除 |
| **Admin（管理者）** | 役員 / 部長 | メンバー招待 / 全目標CRUD / 全タスク確認 |
| **Manager（マネージャー）** | チームリーダー / 店長 | 月次・半期目標CRUD（年次以上はread）/ メンバーへのタスク割当 |
| **Member（一般メンバー）** | 一般社員 | 目標read（自分の上位目標）/ 自タスクCRUD / 自分への割当タスク確認 |

### 3.2 細粒度パーミッション（JSONB）

```json
{
  "goal": {
    "long_term": { "view": true, "edit": false, "delete": false },
    "yearly":    { "view": true, "edit": false, "delete": false },
    "half_year": { "view": true, "edit": true,  "delete": false },
    "monthly":   { "view": true, "edit": true,  "delete": true }
  },
  "task": {
    "assign_to_others": true,
    "view_others_tasks": true,
    "view_org_tasks": true
  },
  "member": {
    "invite": false,
    "remove": false,
    "edit_roles": false
  },
  "ai": {
    "use_org_ai": true,
    "use_personal_ai": true,
    "monthly_cost_limit_yen": 5000
  },
  "billing": {
    "view": false,
    "manage": false
  },
  "audit": {
    "view_log": false
  }
}
```

Ownerが GUI でメンバーごとに細かく設定変更可能。プリセットロールは初期値。

### 3.3 階層的目標カスケード

```
[Org Long-term (Owner only)]
   ↓ 連動
[Org Yearly (Owner / Admin)]
   ↓ 連動
[Team Half-year (Admin / Manager)]
   ↓ 連動
[Personal Monthly (Manager / Member)]
   ↓ 派生
[Daily Tasks (Member)]
```

下位レベル目標作成時に上位を選択して紐付け → 組織全体の目標がツリー構造に。CEOが上から下までの達成度を見渡せる。

## 5. データ分離設計 ⭐企業向け最大の差別化

### 5.1 3階層のデータ分離保証

| 層 | データ保管場所 | AI参照範囲 | 退職時挙動 |
|---|---|---|---|
| **L1 個人** | 共有Supabase / `user_id` RLS | 自分の `user_memory` のみ | N/A |
| **L2 SMB** | 共有Supabase / `org_id` RLS分離 | 組織コンテキスト内のみ。個人モードのデータは見ない | デバイス側自動ログアウト、サーバー側に残す（再雇用対応） |
| **L3 Enterprise** | **専用Supabaseプロジェクト**（オプション）OR 厳密RLS + 暗号化 | 完全に閉じた組織空間 | デバイスから即時削除 + サーバー側もハードデリート可 |

### 5.2 L3 専用Supabaseインスタンス

最大の差別化軸。営業トーク：「貴社のデータは物理的に隔離されたサーバーで管理されます」。

- 別Supabaseプロジェクト発行（顧客ごと）
- バックアップも独立
- データ移管・廃棄も顧客主導
- 月額に+¥100,000程度オプション

### 5.3 企業バイヤーの典型的な懸念と回答

| 懸念 | 実際のリスク | 訴求方法 |
|---|---|---|
| 「他社のAIに送信される」 | 業界標準だが疑問は持たれる | Anthropic Claude / Whisper はLLM学習に使われない旨を明記 |
| 「自社データが個人ユーザー側に漏れる」 | 設計次第で発生する | **データ分離の技術設計を明示**（上記表） |
| 「退職者のスマホに残る」 | あり得る | 強制ログアウト機能 + キャッシュ削除 |
| 「全データのコピーを取れない」 | 囲い込みリスク | エクスポート機能（CSV/JSON/API） |

### 7.4 「DB肥大化問題」への対処

長期運用で AI コストより DB コストが上回るリスクへの対策：

1. **AI 会話ログの 90日剪定**（cron で自動削除）
2. **完了タスク 2年後のコールドストレージ移行**（Postgres → S3 互換ストレージ）
3. **AI メッセージは text only 保存**（tool_use ブロックは捨てる、既存設計を継承）
4. **要約による圧縮**: 古い目標達成記録は要約文に変換して原文削除
5. **org_memory** で「傾向」を保存することで、AI に毎回送る情報量を削減
6. **プロンプトキャッシュ最大活用**（Anthropic 90%割引）

## 9. アプリ構成（モノレポ + Variant ビルド）

### 9.1 物理構成

```
モノレポ:
  packages/
    shared/      ← 80%は共通（UI部品、型、ユーティリティ）
    biz/         ← 組織機能（L2/L3 で共通）
    enterprise/  ← L3 専用（SSO、監査ログ、専用インスタンス管理）
    supabase/    ← migrations, Edge Functions
  
  apps/
    tosche/      → L1 個人 + L2 SMB（Biz拡張は組織コードでアンロック）
    tosche-biz/  → L3 専用アプリ
```

### 9.2 Expo Variant ビルド

```bash
EXPO_VARIANT=personal expo prebuild  → App Store: ToSche
EXPO_VARIANT=biz      expo prebuild  → App Store: ToSche for Biz
```

両者は：
- **同じコード**（条件分岐は環境変数フラグで最小限）
- **同じSupabase / DB**（RLSと `org_id` で論理分離、L3 オプションで専用DB）
- **同じ auth.users テーブル**（1ユーザーが両方使える）
- 異なる **アプリアイコン・名前・ストア掲載**
- 異なる **デフォルトUI**（Bizは個人モード非表示、Personal は組織機能を「+ 企業契約を追加」リンクのみ）

### 9.3 App Store 戦略

- **ToSche**（L1/L2 個人向け+SMB拡張）: フリーミアム、消費者向けマーケ
- **ToSche for Biz**（L3 法人向け）: 営業誘導前提、ストア検索流入は少なくてOK、説明文は完全B2B文体

## 11. リスクと緩和策

| リスク | 緩和策 |
|---|---|
| **B2B営業力不足** | SmartHR・freee 等の人事SaaS開発出身者を業務委託で雇用、もしくは Sansan 等の名刺アプリと提携 |
| **個別カスタマイズ要求の氾濫** | Phase 1-5 は標準機能で固定、カスタムは Phase 6 以降の別契約 |
| **SSO / コンプライアンス要件** | 早期に SAML 対応着手、ISO 27001 / Pマーク取得をロードマップに含める |
| **DB 肥大化** | 7.4 の剪定戦略を最初から組み込む |
| **個人版とのコード分岐** | モノレポ + Variant ビルドでコードベースは1つに統一 |
| **顧客の脱退（解約）** | 全データのCSV/JSON エクスポート機能を提供、囲い込みではなく価値で勝つ |
| **AIコスト暴騰** | 月額上限ハードキャップ + プロンプトキャッシュ徹底 |
| **L2/L3 カニバリゼーション** | L2 に明確な天井を設定（30名・SSO無し・API無し） |
| **データ分離訴求が伝わらない** | 営業資料・契約書テンプレに技術設計を明記、Pマーク等の認証取得 |

## 12. 次のステップ（B2B 着手前に確認すること）

1. **市場調査**：競合ツールとの差別化ポイント最終確認
2. **パイロット顧客3社の打診**：友人経営者ネットワークから選定
3. **法務整備**：利用規約・SLA・データ処理契約書（DPA）のテンプレ作成
4. **資金確保判断**：自己資金 or 外部調達で Phase 1-6 の ¥30-50M を確保
5. **MVP範囲確定**：Phase 1+2+3 のみで MVP リリース、Phase 4 以降は要望ベース
